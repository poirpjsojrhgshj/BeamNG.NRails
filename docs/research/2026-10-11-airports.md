# Airports and runways: OurAirports data, graded runway surfaces, markings (2026-10-11)

Groundwork for docs/ROADMAP.md quick win 4 "Airports and runways" (for plane mods; the owner flies
planes). Branch `feature/airports`. Built offline: nothing here touches the game, and nothing is wired
into earthd or the mod yet (§6 is the plan for that).

New modules (no existing module changed except one host policy in `netfetch.POLICIES` and one entry
in `cache.KEPT`):
- `server/airports.py`: download, cache and refresh of the OurAirports files; parsing into runways and
  helipads; spatial queries; the CLI.
- `server/runwaygeom.py`: runway frame, zones, the fitted longitudinal profile, the graded height
  field and its blend into the terrain (pure numpy).
- `server/runwaymarks.py`: the painted markings as stroke geometry (pure).
- `server/airportpreview.py`: the CLI's top-down preview.
- Tests: `server/tests/test_airports.py`, `test_runwaygeom.py`, `test_runwaymarks.py`, with the
  synthetic files of `airportfixtures.py` (no network).

Markers: **[V]** verified in this session (run, measured or read), **[I]** inference or a number taken
from memory of a standard that was not re-read here.

## 1. The data: OurAirports

### 1.1 Where and under what terms [V]
- `https://ourairports.com/data/` itself could not be read directly on 2026-10-11: **its TLS certificate had
  expired** (`CERTIFICATE_VERIFY_FAILED ... certificate has expired`; plain http timed out). Its text was read
  from the Internet Archive capture of 2026-09-29 (`web.archive.org/web/20260929232328/https://ourairports.com/data/`),
  the data dictionary from the capture of 2026-10-09. TLS was not bypassed.
- Terms of use, verbatim: **"All data is released to the Public Domain, and comes with no guarantee of accuracy
  or fitness for use."** The page adds: "We'd love you to give us credit, like we give credit to our sources,
  but you're not required to." We credit it anyway (CREDITS.md, `airports.CREDIT`).
- "Effective 3 November 2021, the download files are stored on GitHub, in the repository
  davidmegginson/ourairports-data. The old download links redirect to there." The links on the page are
  `https://davidmegginson.github.io/ourairports-data/<file>.csv`; the repository README lists the same and says
  the files are generated daily (GitHub only updates them when the content changes). GitHub reports that
  repository's licence as **The Unlicense** (api.github.com, read 2026-10-11).
- Response headers (2026-10-11): `content-type: text/csv; charset=utf-8`, `last-modified: Sun, 11 Oct 2026
  01:53:57 GMT`, an `etag`, `cache-control: max-age=600`; gzip is served on request.
- All requests (including this research) went through `netfetch.Fetcher` with a polite policy; the shipped one is
  `POLICIES["davidmegginson.github.io"]`: 0.2 req/s, burst 2, one at a time, daily soft budget 20 / hard 40,
  2 attempts with a 5 s base backoff, `binary=True` (an HTML page instead of CSV is an error, not data),
  `offline_ok`. A weekly refresh is 2 requests.

### 1.2 Columns (data dictionary) [V]
- airports.csv: `id` (persistent integer), `ident` (ICAO code if any, else a local code, else e.g. `AU-0220`),
  `type` (`large_airport`, `medium_airport`, `small_airport`, `heliport`, `seaplane_base`, `balloonport`,
  `closed`), `name`, `latitude_deg`, `longitude_deg`, `elevation_ft` (**feet**), `continent`, `iso_country`,
  `iso_region`, `municipality`, `scheduled_service`, `icao_code`, `iata_code`, `gps_code`, `local_code`,
  `home_link`, `wikipedia_link`, `keywords`.
- runways.csv: `id` (persistent), `airport_ref`, `airport_ident`, `length_ft` ("of the full runway surface
  (including displaced thresholds, overrun areas, etc)"), `width_ft`, `surface` ("not yet a controlled
  vocabulary"; ASP, TURF, CON, GRS, GRE, WATER, UNK...), `lighted` (1/0), `closed` (1/0), and per end
  (`le_` = low-numbered, `he_` = high-numbered): `ident`, `latitude_deg` / `longitude_deg` ("centre of the ...
  end of the runway, if available"), `elevation_ft`, `heading_degT` (**true**), `displaced_threshold_ft`.
- Helipads are rows of runways.csv (`le_ident` H1, H2...).

## 2. The runway model (`airports.Runway`)

- Ends `le` / `he`: lat, lon, elevation (m: `elevation_ft` × 0.3048; else the airport's elevation, flagged;
  else none and the DEM decides), true heading (a landing on this end; from the ends' bearing when both are
  given), displaced threshold (m), position `data` / `computed`.
- `length_m`: the ends' distance when both are surveyed (the data's `length_ft` is kept as
  `length_data_m`; 5 % / 30 m apart -> `length_mismatch`); else `length_ft`.
- Missing ends:
  - one end + its (or the other end's reversed) true heading + the length -> the other end is computed
    (`derived`);
  - no end, but a heading, a length and the airport has only this runway -> centred on the airport reference
    point (`arp`, an estimate: the FAA puts the ARP at the runways' geometric centre, but OurAirports' points
    are often the terminal). Excluded from queries unless asked (`min_quality="arp"`);
  - anything else is skipped and counted. A designator alone (no heading) is not used: the number is the
    magnetic heading and the declination reaches 20° in places.
- `width_m`: the data's, else (and when > half the length or > 120 m) the ICAO minimum per code number: paved
  18 / 23 / 30 / 45 m for codes 1-4, unpaved 15 / 18 / 23 / 30 m (`width_source = "default"`).
- `surface`, `condition`, `ground_model`, `paved`, `surface_known`, `lighted`, `closed`, `flags`.
- Ids and order: rows sorted by OurAirports' persistent integer ids; `Runway.key = "oa:<id>"`. The whole
  `AirportDB` is a pure function of the two files (a test shuffles the rows: identical runways); its
  `snapshot` id is a hash of both files' bytes.
- Helipads (`airports.Helipad`): position from `le_` or the airport's point, size, surface.

## 3. Geometry and grading (`runwaygeom.py`)

### 3.1 Frame and zones
Per runway the ENU tangent plane at its midpoint (`geodesy.EnuFrame`), then s along the runway from le
(0 .. L) and t across it (positive to the left looking from le to he). Zones:

| zone | extent | height |
|---|---|---|
| 4 runway | \|t\| <= W/2, 0 <= s <= L | profile(s) - crown × (sqrt(t² + 1 m²) - 1 m): a crown at 1.25 % (paved) / 2 % (unpaved), its ridge rounded over ~1 m |
| 3 shoulder | to W/2 + S (paved only: S = 3 / 6 / 7.5 / 10.5 m for W < 30 / >= 30 / >= 45 / >= 60 m) | falling at 2.5 % from the runway edge |
| 2 graded strip | to G from the centreline (75 m codes 3-4, 40 m code 2, 30 m code 1) and E beyond each end (60 m; 30 m code 1) | the terrain clamped to within strip_slope × d of the pavement's height at its nearest point (d = distance from the pavement; strip_slope 2.5 % codes 3-4, 3 % codes 1-2); beyond the ends the profile's end grade continues |
| 1 blend | a further B (20-250 m per runway) | dem + w (strip - dem), w = 1 - smoothstep(b / B) |
| 0 | outside | the DEM, bit for bit |

B = clamp(1.5 × max \|strip - dem\| on the strip's edge / 0.25, 20 m, 250 m): the smoothstep's steepest
slope is 1.5/B, so the blend adds at most 1:4 (25 %) to the terrain's own slope (plus, inside it, the strip
band's own growth: terrain cross slope minus strip slope; a test bounds both). The field is continuous
everywhere (the clamp is continuous, w = 1 at the strip's edge and 0 at the blend's), so no step reaches the
heightmap; a test walks transects at 0.25 m on a tilted, wavy synthetic hillside and finds no jump.

| max grade on any portion | 1.25 % | 1.5 % | 2 % | 2 % | 3.1.14 (0.8 % in the first and last quarter on precision runways, reported, not enforced) |
| vertical curve radius (0.1 / 0.2 / 0.4 % per 30 m) | 30,000 m | 15,000 m | 7,500 m | 7,500 m | 3.1.17 |
| graded strip half-width | 75 m | 75 m | 40 m | 30 m | 3.4.8 (2018) |
| strip beyond the end | 60 m | 60 m | 60 m | 30 m | 3.4.2 |
| strip transverse slope | 2.5 % | 2.5 % | 3 % | 3 % | 3.4.17 |
| runway transverse slope | 1.25 % used (FAA 1.0-1.5 %, ICAO 1-1.5 % letters C-F, 2 % A/B) | | | | FAA AC 150/5300-13B, ICAO 3.1.20 |
| shoulders | 3-10.5 m by width (FAA design groups I-VI: 10 / 10 / 20 / 25 / 35 / 40 ft), 2.5 % fall | | | | FAA AC 150/5300-13B |
Code numbers come from the runway length (the aeroplane reference field length is not in the data). Verify the
values against the current Annex 14 and AC before quoting them elsewhere; the code only depends on them through
`LIMITS`.

### 3.3 The longitudinal profile
1. The DEM along the centreline every ds = clamp(L/300, 3 m, 15 m): at each station 5 samples across the
   runway (-W/2, -W/4, 0, W/4, W/2), each turned into the centreline height it implies with this runway's crown,
   and their median (a real crowned runway in a lidar DEM is lower at its edges; a stray pixel does not count).
2. End heights: the DEM's level at each end (a line fitted over the last 50 m, taken at the end). When the data
   has both end elevations and they agree with the DEM (end-to-end difference within max(10 m, 3 % L), common
   offset <= 60 m), the ends become **the data's end-to-end difference at the DEM's level** (the data's
   elevations minus their mean offset from the DEM). Otherwise the DEM's ends (`target_source` says why).
3. A Whittaker smoother of the DEM's residual from the line between the ends (least squares + λ × curvature²,
   both ends pinned), with the **smallest λ whose profile keeps radius >= the code's and grade <= max(the
   code's max grade, \|overall\| + 0.25 %)** (bisection over λ = 10^18 .. 10^0 in quarter decades; the
   stiffest profile is the straight line, which always passes).
4. Non-standard runways:
   - **steep**: overall grade above the code's end-to-end limit (altiports, bush strips): radius >= 400 m
     (0.23 g at 30 m/s), no grade limit, and a narrow strip (pavement + 7.5 m, 15 m beyond the ends) instead of
     the ICAO strip;
   - **relaxed**: an unpaved runway whose standard profile leaves the terrain by more than 1.5 m (backcountry
     strips follow their valley): the same radius / grade rule as steep, the normal strip;
   - **coarse DEM** (`dem_res` > 10 m, e.g. the SRTM-class AWS fallback): the relaxed radius becomes >= 50 ×
     the pixel size (1,500 m at 30 m), because the DEM's shape there is resampling steps, not the runway.
5. Statistics per plan (`Plan.stats`): grades (max, first/last quarter), min radius, RMSE / max deviation from
   the DEM, data - DEM at each end, the strip's largest edge change, B, the limits applied, the ICAO checks.

### 3.4 Several runways
`runwaygeom.groups()` partitions runways whose influence rectangles (+ B_MAX + 30 m) overlap, transitively;
`AirportDB.group(rw)` builds a runway's group from the whole file, so any cell or block grades the same set in
the same order. In a group: longest first (then by id); each runway is fitted on the field graded by the ones
before it, and graded over it except inside the earlier runways' paved areas, fading over 30 m around them, so a
crossing takes the main runway's surface (exactly: a test compares bit for bit) and the secondary's crown meets
it within the fade. Parallel runways' strips simply compose.

### 3.5 Known limits
- Water at runway ends (Gibraltar): the strip and blend raise the sea by up to 1.4 m (the DEM's sea is 0 m). A
  water mask (WorldCover 80 / Overture water from MapData) should hold the strip off water; the sea surface is
  drawn separately anyway.
- Taxiways, aprons, buildings: not graded (§6.8).
- OurAirports positions are 4-8 decimals (11 m - 1 mm); grass strips overlap where two parallel strips are
  drawn too close (White Waltham 07L/25R and 07R/25L).
- The DEM's own artefacts (bridges over a runway, a DSM's trees in coarse DEMs) pass into the profile within
  the radius limit.

## 4. Markings (`runwaymarks.py`)

### 4.1 What is painted
Strokes (a segment in (s, t) and a width; the painted area is the rectangle around it) per element, standard by
the airport's country (FAA AC 150/5340-1M for US territories, ICAO Annex 14 §5.2 elsewhere) [I: dimensions from
memory, see `runwaymarks.STYLES`]:

| element | FAA | ICAO | who gets it |
|---|---|---|---|
| threshold stripes | 45.7 m × 1.75 m from 6.1 m | 30 m × 1.8 m from 6 m | precision, non-precision, visual codes 3-4 |
| stripes by width | 4 / 6 / 8 / 12 / 16 for < 23 / 30 / 45 / 60 m / wider, centre gap doubled | same | |
| designation | number 18.3 m high (12.2 m narrow), "9" | 9 m high, "09" | all paved; side letter nearest the threshold; seven-segment font; the data's ident, else true heading / 10 (flagged: real numbers are magnetic) |
| centreline | 36.6 m / 24.4 m gaps | 30 m / 20 m | width 0.9 (precision) / 0.45 (non-precision) / 0.3 m (visual), laid symmetrically between the designations |
| aiming point | 45.7 × 9.1 m at 310.9 m, 21.9 m apart | ICAO table 5-1 by landing distance: 150-400 m out, 4-6 m wide, 6-18 m apart | precision, non-precision, visual >= 1200 m |
| touchdown zone | 3-3-2-2-1-1 stripes per side every 152.4 m, 22.9 × 1.83 m | every 150 m, 22.5 × 3 m, 1-6 pairs by landing distance | precision; a pair on the aiming point's place or past half the landing distance is left out |
| side stripes | 0.9 m (0.45 m < 30 m), outer edge on the runway edge (30 m out on wider runways) | same | precision |
| displaced threshold | 3.05 m bar + centreline arrows | 3 m bar + arrows | when the data has one (> 40 % of the runway: ignored, noted) |
| closed | yellow crosses | white crosses | 36 m arms, at both ends and every <= 300 m; nothing else |

Marking class from the data (OurAirports has no approach type): `precision` = lighted, paved, >= 1800 m, large or
medium airport; `nonprecision` = lighted, paved, >= 1200 m; `visual` = other paved; `unpaved` = nothing (cones,
boards: props later); `closed`. Tests: every stroke on the pavement, no two elements overlap, the two ends exact
mirror images, stripe counts per width, displaced thresholds, closed runways, determinism.

Counts at the test places: KBWI 10/28 142 strokes, KLAX 7L/25R 173, LXGB 90, VNLK 30 (designations + centreline).

### 4.2 How to paint them in the game (from docs/research/2026-10-11-engine-probes.md)
- **DecalRoads, one per stroke** (2 nodes, width = the stroke's): P1 says they render on the hidden physics
  block with the edges within ±1 mm of the physics ground and no z-fighting against our mesh tiles
  (`overObjects=false`, tiles keep `decalType='None'`); P2: they re-clip by themselves when the block is
  re-imported or patched (~1 µs per edge), so terrain-follow commits need no runway code; P3: create with
  `registerObject` -> `insertNodeNoRegen` -> `regenerate` (~0.15 ms for a short road, the clip inside the call),
  so a 150-stroke runway is ~20-40 ms, time-sliced by the governor over a few frames; P4: a rebase recreates them
  (translation alone is not enough). A white material: the stock `line_white` (decalroad.zip) or a runtime
  material with a white texture; crosses in yellow.
- **Decal instances** (P8: `addDecalTangent` 0.025 ms, 19 µs with the ground ray) suit the digits better as
  textured glyphs (one square decal per character, a runtime atlas in `/temp`): untested with our own
  texture -> probe before switching.
- **Terrain layers** are for the physics, not the paint (2 m cells): the runway rectangle's ground model (§6.3).
- **Far away** the satellite imagery already shows the real markings (NAIP 0.6 m), so decals are needed only
  near the player (within ~2 km, the decal `distanceFade`); beyond, the photo. Where the data's coordinates are
  metres off the photo's runway, near decals and far photo would disagree: a later check of the runway against
  the imagery (or OSM's runway polygon) should gate the decals.

Timings (this machine, DEM on disk): whole preview 0.1 s (one small runway) to 2.1 s (KBWI, 1601 × 1357 px);
plan per runway 13-56 ms (first runway of a place includes reading its DEM tiles); `apply` 7 ms (a 0.15 M point
small field) to 0.58 s (2.2 M points, 4 runways). Cold (DEM downloads): KLAX 4.2 s, LXGB 1.5 s, others 0.9-2.1 s.
Load of the airport data 1.6-1.9 s, `near()` 0.7-1.3 ms.

Findings:
- Where the DEM is lidar, the data's end elevations and the DEM agree to about a metre, and the fitted profile
  stays within 0.04-0.22 m RMSE of the DEM: grading mostly removes noise and the crown is ours.
- The standard limits would have buried Johnson Creek's top end and cut Courchevel's knee flat; the steep /
  relaxed rules keep the real shape.
- SRTM-class DEMs (Nepal, PNG) carry integer-metre steps: without the coarse-DEM radius rule Lukla came out at
  20 % max grade with steps along it; with it, 14.7 %.
- The first version levelled the strip at the end height: at Lukla that cut 25 m into the slope beyond the top
  end; the strip now continues the end grade (and is narrow on steep runways).

## 6. Integration plan

### 6.1 Server side
- One `airports.Store` per server on the server's `Fetcher` and cache dir; `load()` in a worker at start (1.6-1.9 s
  parse; the copy on disk is used at once, the weekly refresh runs as kind `background`). A `--airports on|off`
  flag (default on once the in-game checks pass).
- Plans per **group** (`AirportDB.group`), cached in memory by (group runway ids, `db.snapshot`,
  `airports.VERSION`, a runwaygeom version constant to add, the DEM sampler's identity). The profile's DEM sampler
  must be **fixed per place** (one zoom, `dem.zoom_for(lat, 2 m)` = z15 almost everywhere, and the same source
  chain) and not the block's or a tile's own zoom, so the plan is the same whichever block or tile asks first.
  `dem_res` from the provider that served those tiles (Mapterhorn below z15 or the AWS fallback = coarse).

### 6.2 The physics heightmap and the mesh tiles (exact match)
- `heightmap.generate(frame, elev_fn, ...)` and `heightmap.surface()` take `elev_fn(lat, lon)`. earthd wraps the
  DEM's sampler: `runwaygeom.graded_elev_fn(elev_fn, plans)` with the plans of every group touching the block.
  **heightmap.py does not change.** `apply` touches only points inside each plan's lat/lon box and returns the
  DEM bit for bit elsewhere (tested), so blocks away from airports are byte-identical to today.
- The mesh tiles at the exact level (L-1, the 2 m physics lattice) sample their vertices through the same wrapped
  function at the same lattice points, so their vertices equal the heightmap's samples bit for bit (as
  `test_heightmap` / the M4 drive check for the DEM today). Coarser tiles sample the same function at their own
  vertices (an approximation of the graded field, as they are of the DEM).
- The hook is in earthd (where the block's and the tiles' `elev_fn` are built), which the v1.4 M6 branch is
  rewriting: wire it after M6 merges, at the one place both call. `test_runwaygeom.test_heightmap_dropin`
  already runs `heightmap.grid_u` with the wrapped function.
- Quantisation: the runway surface goes through the block's height quantum like any terrain (1/64 m default):
  the crown and grades survive it.

### 6.3 Surfaces (ground models) in the terrain layers
- The 8-layer import costs **+4-5 ms per 512² commit** (probe "8-layer terrain import": 20.8-22.6 ms against
  16.5-17.8 ms with one layer; 8 greyscale masks, not packed RGBA); PT1 showed the wheels' contact material
  following the layer (and `setMaterialIdxWs` patches with no `reloadCollision`).
- Plan: when v1.5 brings the layer masks, the runway's paved zones (4 and 3, from `apply`'s zone output) paint the
  runway's ground model (ASPHALT / GRASS / GRAVEL / DIRT / SAND / ASPHALT_OLD...) into the masks the server
  writes for the block; the strip falls to land cover (usually GRASS). Runway layers are a subset of v1.5's
  set (ASPHALT, GRAVEL, DIRT, SAND, GRASS, MUD, ROCK, SNOW: COBBLESTONE / METAL / WOOD / ICE runways map to the
  nearest of those).
- Until v1.5: a per-commit `setMaterialIdxWs` corridor is too slow for big runways (P10: 0.39 µs per cell plus the
  updates; KLAX's 4 runways with shoulders ≈ 0.17 M cells ≈ 65 ms before the grid updates), so the layer masks
  are the way.

### 6.4 When to apply (map-data cells)
- Per z14 cell (`mapcells`), `AirportDB.groups_in_cell(key)` gives the whole groups whose influence footprint
  (strip + B_MAX) touches it (an exact rectangle test, ~2 ms). A block or tile takes `mapcells.cells_for_bbox`
  of its footprint and the union of their groups (deduplicated by runway ids). As cells are the map-data unit,
  MapData's `CellData` can carry the cell's runway groups next to its layers (the snapshot id in its provenance).
- Prefetch with the map-data cells ahead of the player.

### 6.5 Interaction with v1.4 M6 global tiles
- Tile content stays a pure function of position + versioned inputs: add the OurAirports snapshot id and the
  runwaygeom version to the tile content key (with the DEM's). Runway grading is keyed on global runway ids and
  lat/lon only (never the anchor, the tile key or the load order), so an M6 tile built anywhere, any time,
  grades the same; a weekly data refresh changes only the tiles under changed runways (their key changes).
- A global tile's coarse vertices sample the graded function; the near exact-level tiles stay on the physics
  lattice as today.

### 6.6 Markings, spawn points, helipads
- Markings: the server sends a runway's strokes as lat/lon pairs (`runwaymarks.to_world`) for groups within ~2 km
  of the player; the mod turns them into DecalRoads in the anchor frame, time-sliced, recreated on rebase,
  removed beyond ~3 km. Per runway one message; ~150 roads for a big runway.
- Spawn points: each runway end (threshold, after the displaced part) as a place with the runway heading, in
  `places.lua`'s list ("KBWI 28"); helipads as spawn points for helicopters.
- An "aircraft" mode for the edge guard (it already leaves airborne vehicles alone).

### 6.7 Physics and planes
- Plane mods take off at 50-90 m/s: the graded profile's radius limits (7,500-30,000 m standard, >= 400 m steep)
  keep vertical accelerations below 0.1 g on standard runways.
- The physics block (512², 1 km) covers a big runway only in part; a take-off run of 3 km crosses two or three
  terrain-follow commits at 60-80 m/s (the 512 follow table handles 134 m/s).

### 6.8 Later: airport buildings, taxiways, aprons
- Overture `base/infrastructure` carries OSM's aeroway features [I: verify the classes: aerodrome, runway,
  taxiway, apron, helipad, hangar...] and `buildings` the terminals and hangars; MapData already reads both per
  cell. Taxiways and aprons: graded like runways with their own (gentler) limits and painted lines (yellow
  centrelines, holding positions). OSM runway polygons can also place the 24,000 runways OurAirports cannot
  (mostly small and bush strips in Brazil, Australia, PNG, Chile, China) and cross-check its coordinates.
